# 0001. Один мультимодульный Gradle-билд, а не проект на сервис

**Статус:** принято

## Контекст

Четыре сервиса и общий контракт событий живут в одном репозитории. Нужно решить, как их
собирать: одним билдом, четырьмя независимыми или композитной сборкой.

## Решение

Один мультимодульный Gradle-билд. Версии зависимостей — в `gradle/libs.versions.toml`,
общие настройки модулей — в convention-плагинах `build-logic/`, а не копипастой в четырёх
`build.gradle.kts`.

## Последствия

- `./gradlew build` собирает и проверяет всё разом — CI укладывается в одну джобу.
- `events-contract` подключается обычным `project(":events-contract")`, без публикации артефакта.
- Версии не расползаются: обновление Spring Boot — одна строка в каталоге.
- Независимость деплоя сохраняется там, где она действительно нужна, — на уровне образов:
  свой `Dockerfile` и своя запись в матрице релиза у каждого сервиса.
- Плата: репозиторий выглядит монолитнее, чем «настоящие микросервисы в разных репо».

## Альтернативы

- **Четыре независимых проекта.** Честнее для сервисов в разных репозиториях, но в монорепо
  даёт только четыре набора версий и четыре CI-конфига.
- **Композитная сборка.** Компромисс, у которого здесь нет выигрыша: подключать общий модуль
  всё равно пришлось бы, а конфигурация усложняется.
